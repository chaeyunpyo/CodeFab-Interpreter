# [추가] 실행전 최적화 구현 항목

## 구현해야 할 최적화

| 분류 | 항목 | 설명 | 효과 |
| --- | --- | --- | --- |
| 정적 바인딩 | 변수 거리(distance) 계산 | Checker Unit에서 지역 변수가 몇 단계 위 스코프에 있는지 미리 계산 | 조회 O(depth) → O(1) |
| 상수 연산 최적화 | 수식 합치기 | 런타임 이전에 100% 확정되는 리터럴 연산을 미리 계산해서 리터럴로 치환 | 루프 안 반복 연산 제거 (예: 800만 → 100만 연산) |

## 구현해야 할 검증 (Test Double)

| 분류 | 항목 | 설명 |
| --- | --- | --- |
| 정적 바인딩 검증 | 조회 경로 검증 | 스코프를 거슬러 올라가지 않고 계산된 위치로 즉시 접근하는지 확인 |
| 수식 합치기 검증 | 연산 횟수 검증 | 실행 중 연산 호출 횟수가 N회에서 0회로 줄었는지 확인 |

## 적용 조건

- 상수 연산 최적화는 표현식의 결과가 런타임 이전에 100% 확정될 수 있는
  경우에만 적용한다 (변수가 섞인 표현식은 대상이 아님).
- 정적 바인딩은 지역 변수 조회에 대해서만 적용한다.

## 적용 가능한 디자인 패턴 (가산점)

> 디자인 패턴은 여러 곳에서 발생될 수 있는 문제를 해결하는 일반화된
> 모범 사례입니다. GoF 디자인 패턴을 사용하면 약간의 추가 점수가
> 주어집니다 (`유의사항.md` 참고).

| 패턴 | 적용 지점 |
| --- | --- |
| Visitor Pattern | 정적 바인딩(거리 계산)과 상수 연산 최적화는 둘 다 "AST 전체를 한 번 훑으며 노드마다 처리한다"는 점에서 같은 모양이다. Checker가 이미 쓰고 있는 "타입 -> 처리 함수" 딕셔너리 구조(`_stmt_handlers`)를 Expr에도 동일하게 적용하면 사실상 Visitor Pattern이 되고, 이 두 최적화를 같은 순회 골격 위에서 구현할 수 있다. |
| Strategy Pattern | Test Double 검증 시, "진짜 Storage/Expr 평가" 대신 호출 횟수만 세는 가짜 구현으로 갈아끼우는 것 자체가 Strategy 패턴의 활용 사례다. |
