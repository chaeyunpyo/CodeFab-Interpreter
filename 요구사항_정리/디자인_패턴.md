# 적용된 GoF 디자인 패턴 정리

`유의사항.md`의 가산점 항목("GoF 디자인 패턴 적용") 대응 문서. 각 기능
문서(`function.md`, `class.md`, `import.md`, `실행전_최적화.md`,
`공장제어쉘.md`) 하단에 패턴별로 흩어져 있던 내용을 한곳에 모아, 실제
코드 어디에 어떻게 적용됐는지 정리한다.

## 요약

| 패턴 | 적용 지점 | 개수 |
| --- | --- | --- |
| Strategy (Command) | `LoxCallable` — Function/LoxClass/ArrayBuiltin 호출 통합 | 1 |
| Strategy (표 기반 분기) | Executor/Checker/Parser의 "타입 -> 처리 함수" 딕셔너리 | 1 |
| Visitor | Executor/Checker가 AST를 순회하며 노드 타입별로 처리 | 1 |
| Chain of Responsibility | 클래스 상속 체인을 따라 올라가며 메서드/instanceof 판정 | 1 |
| Facade + Registry | `Importer` — 파일 읽기+조립+검사+캐시를 한 진입점으로 감춤 | 1 |

## 총 개수

* **5개**

## 1. Strategy(Command) Pattern — `LoxCallable`

**문제**: 함수 호출(`add(1, 2)`)은 사용자 정의 함수(`Func`), 배열 생성자
(`Array(3)`), 클래스 생성자(`Robot()`)를 전부 같은 문법(`CallExpr`)으로
표현한다. `CallExpr`을 평가하는 코드가 "호출 대상이 함수인지, 배열
빌트인인지, 클래스인지"를 `isinstance` 사슬로 구분하면, 새로운 호출
가능한 대상이 추가될 때마다 그 사슬을 계속 늘려야 한다.

**해결**: `arity()`(파라미터 개수)와 `call()`(실제 호출) 두 메서드만
정의한 추상 인터페이스 `LoxCallable`(`src/executor/_callable.py`)을
만들고, 호출 가능한 값들이 전부 이를 구현한다.

| 구현체 | 파일 | `call()`이 하는 일 |
| --- | --- | --- |
| `Function` | `src/executor/_function.py` | 사용자 정의 함수 본문 실행 |
| `LoxClass` | `src/executor/_class.py` | 인스턴스 생성 + `init` 호출 |
| `ArrayBuiltin` | `src/executor/_array.py` | `FabArray` 생성 |

`_evaluate_call`(`src/executor/_expr.py`)은 호출 대상이 무엇이든 구분
없이 이렇게만 처리한다.

```python
if not isinstance(callee, LoxCallable):
    raise NotCallableError(expr.paren)
if len(arguments) != callee.arity():
    raise ArityMismatchError(callee.arity(), len(arguments), expr.paren)
return callee.call(storage, arguments)
```

**효과**: 새 호출 가능한 타입(예: 향후 람다)이 추가돼도 `_evaluate_call`은
전혀 안 바뀌고, `LoxCallable`만 구현하면 된다 — 개방-폐쇄 원칙.

## 2. Strategy Pattern — "타입 → 처리 함수" 표 기반 분기

**문제**: Stmt/Expr 종류가 늘어날수록(현재 Stmt 10종, Expr 15종)
`if isinstance(stmt, XxxStmt): ... elif isinstance(stmt, YyyStmt): ...`
사슬이 계속 길어지고, 새 타입을 추가할 때마다 기존 분기 코드를 건드려야
한다.

**해결**: "타입 → 그 타입을 처리하는 함수" 딕셔너리를 만들고, 분기 로직은
"표에서 찾아서 호출한다" 한 줄로 통일한다. 이 프로젝트 곳곳에 같은 모양이
반복해서 나온다.

| 위치 | 표 이름 | 무엇을 처리하는가 |
| --- | --- | --- |
| `src/executor/_stmt.py` | `_STMT_EXECUTORS` | Stmt 타입 → 실행 함수 |
| `src/executor/_expr.py` | `_EXPR_EVALUATORS` | Expr 타입 → 평가 함수 |
| `src/checker/_checker_unit.py` | `_stmt_handlers` | Stmt 타입 → 검사 메서드 |
| `src/assembler/_statement_parser.py` | `_statement_factories` | 문장 시작 키워드 → 파싱 메서드 |
| `src/assembler/_expression_parser.py` | `_postfix_factories`, `_infix_factories` | 후위/중위 연산자 토큰 → 조립 메서드 |

예 (`src/executor/_stmt.py`):

```python
_STMT_EXECUTORS: Dict[Type[Stmt], Callable[[Any, Storage], None]] = {
    ExpressionStmt: _execute_expression_stmt,
    PrintStmt: _execute_print_stmt,
    ...
}

def execute(stmt, storage):
    handler = _STMT_EXECUTORS.get(type(stmt))
    if handler is None:
        raise NotImplementedError(...)
    handler(stmt, storage)
```

**효과**: 새 Stmt/Expr/문법이 추가되면 표에 한 줄만 추가하면 되고,
`execute()`/`evaluate()`/`statement()`/`_climb()` 같은 기존 분기
함수의 코드는 전혀 건드릴 필요가 없다.

## 3. Visitor Pattern — AST 순회

**문제**: Executor(값 계산/실행)와 Checker(정적 오류 검사)는 서로 전혀
다른 일을 하지만, 둘 다 "AST 트리를 순회하며 노드 종류마다 다른 처리를
한다"는 같은 구조를 공유한다. 이 순회 로직을 Stmt/Expr 클래스 안에
직접 넣으면(전통적인 Visitor 없는 방식), 클래스마다 "실행하기"
메서드와 "검사하기" 메서드를 둘 다 넣어야 해서 AST 노드 정의와 처리
로직이 뒤섞인다.

**해결**: 2번 패턴(표 기반 분기)을 Visitor의 구현 수단으로 그대로
활용한다 — Stmt/Expr 클래스 자신은 순수 데이터(`@dataclass`)로만
남기고, "누가 순회하느냐"(Executor vs Checker)에 따라 서로 다른
"방문자"(`_STMT_EXECUTORS`/`_EXPR_EVALUATORS` 대 `_stmt_handlers`)가
같은 노드를 다르게 처리한다. `src/checker/_constant_folder.py`의
`ConstantFolder.fold()`도 같은 AST를 세 번째 방식(상수 폴딩)으로
순회하는 또 다른 방문자다.

```python
# 같은 BinaryExpr 노드를,
_EXPR_EVALUATORS[BinaryExpr]   # Executor: 값을 계산
ConstantFolder().fold(expr)    # Checker: 리터럴이면 미리 계산해 접음
```

**효과**: AST 노드 클래스는 "무엇을 하는지"를 전혀 몰라도 되고
(`Expr`/`Stmt`는 필드만 가진 데이터 클래스), 새로운 순회(예: 디버거의
`_walk_stmt`)를 추가해도 노드 클래스를 안 건드린다.

## 4. Chain of Responsibility — 클래스 상속 체인 탐색

**문제**: 메서드 호출(`r.move(5)`)이나 `instanceof` 판정
(`w instanceof Robot`)은 클래스 자신에게 없으면 부모 클래스, 그 부모의
부모까지 계속 올라가며 찾아야 한다. 상속 깊이가 얼마인지 미리 알 수
없다.

**해결**: "내가 처리할 수 있으면 처리하고, 아니면 다음(부모)에게
넘긴다"는 Chain of Responsibility를 상속 체인 위에 그대로 적용한다.

- `LoxClass.find_method`(`src/executor/_class.py`): 자기 `methods`에
  없으면 `self.superclass.find_method(name)`으로 재귀 위임.

  ```python
  def find_method(self, name):
      if name in self.methods:
          return self.methods[name]
      if self.superclass is not None:
          return self.superclass.find_method(name)
      return None
  ```

- `_evaluate_instanceof`(`src/executor/_expr.py`): 인스턴스의 클래스부터
  `superclass`를 따라 올라가며 대상 클래스와 일치하는지 확인.

  ```python
  current = obj.klass
  while current is not None:
      if current is klass:
          return True
      current = current.superclass
  return False
  ```

**효과**: 상속 깊이가 몇 단계든(다단계 상속) 호출하는 쪽은 신경 쓸
필요가 없고, 새 클래스가 상속 체인에 끼어들어도 탐색 로직은 그대로
동작한다.

## 5. Facade + Registry Pattern — `Importer`

**문제**: `import "sum.txt" alias sum;` 한 줄을 처리하려면 파일 읽기 →
Assembler(토큰화+파싱) → Checker(정적 검사) → (재귀적으로) 그 안의
import문까지 같은 과정을 반복 → 캐시 조회/저장 → 순환 참조 감지까지
여러 단계를 거쳐야 한다. 이 전체 과정을 호출하는 쪽(Executor)이 알아야
한다면 책임이 너무 커진다.

**해결**: `src/importer/_importer.py`의 `Importer` 클래스가 이 모든
단계를 감추고 `import_module_with_locals(path)` 하나의 진입점만
노출한다(Facade). 그 안에서 경로별 캐시 `_module_cache`를 Registry로
써서 같은 파일을 다시 읽거나 조립하지 않고, 이 캐시와 별도로
"지금 처리 중인 파일 목록"(`_importing`)을 둬서 순환 import를 감지한다.

```python
def import_module_with_locals(self, path, keyword=None, base_dir=None):
    resolved = self._resolve_module_path(path, base_dir)
    if resolved in self._module_cache:        # Registry: 캐시 히트
        return self._module_cache[resolved]
    if resolved in self._importing:            # 순환 감지
        raise CircularImportError(...)
    ...                                         # 파일 읽기 + Assembler + Checker
    self._module_cache[resolved] = (statements, checker.locals)
    return self._module_cache[resolved]
```

**효과**: `Executor`(`_execute_import_stmt`)는 "경로를 주면 검사까지
끝난 Stmt 목록과 변수 거리 맵을 돌려준다"는 사실만 알면 되고, 파일
I/O/캐싱/순환 감지 같은 세부 사항은 전혀 알 필요가 없다.
