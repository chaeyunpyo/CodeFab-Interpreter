# 개발 순서 및 역할 분담 (5인 기준)

6개 요구사항(function, class, 정적배열, 실행전 최적화, import, 공장제어쉘)
사이의 의존 관계를 기준으로 진행 순서를 정리한다.

## 인원 구성

| 역할 | 인원 | 비고 |
| --- | -- | --- |
| Checker | 1명 | 정적 검사 전담 |
| Assembler | A, B 2명 | 토큰/파싱 전담 |
| Executor | C, D 2명 | 실행 로직 전담 |

이후 모든 표는 이 라벨(Checker, Assembler A/B, Executor C/D)을 그대로 쓴다.

## 한눈에 보기 (5인이 순서대로 할 일)

아래는 각자 위에서 아래로 순서대로 진행하면 되는 요약이다. 바로 밑
"단계별 상세 표"에서 5명을 한 번에 놓고 볼 수 있고, "왜 이 순서인지"는
그 아래 "의존 관계"/"기능별 상세 역할 분담" 절을 참고하면 된다.

**Checker**
1. function 오류 검사 (파라미터 이름 중복, 함수 외부 return)
2. class 오류 검사 (this/super 외부 사용, 자기 상속, 부모 없는 super, init의 return)
3. import 오류 검사 (같은 scope 중복, alias 충돌, 반복문 내부 import)
4. 실행전 최적화 — 정적 바인딩 → 상수 연산 최적화 (순서대로)

**Assembler A**
1. function 파싱 전체 (토큰, 선언, 호출, return)
2. class 파싱 (Class 키워드, 상속, instanceof)
3. 여유가 되면 공장제어쉘 디버그 모드(Stepping) 또는 import 보조

**Assembler B**
1. 정적배열 파싱 ([, ] 토큰, 인덱스 읽기/쓰기)
2. (정적배열 끝나면) 공장제어쉘 파일 모드
3. class 파싱 (필드 접근, this/super)
4. class 파싱이 끝나면 import 파싱+로더로 이동
5. 여유가 되면 공장제어쉘 디버그 모드(Watch)

**Executor C**
1. function 실행 전체 (호출 스코프, 파라미터 바인딩, 재귀, return, 오류)
2. class 실행 (인스턴스·필드 저장소, 생성자 자동 호출)
3. 실행전 최적화 — 변수 조회 로직 변경 또는 Test Double 검증

**Executor D**
1. 정적배열 실행 전체 (Array 생성, 인덱스 읽기/쓰기, 오류)
2. (정적배열 끝나면) 공장제어쉘 파일 모드 보조
3. class 실행 (메서드 호출, 상속 체인, super, instanceof, 오류)
4. Test Double 검증

### 단계별 상세 표

| 단계 | Checker | Assembler A | Assembler B | Executor C | Executor D |
| --- | --- | --- | --- | --- | --- |
| 1단계 | function 오류 검사 | function 파싱 전체 | 정적배열 파싱 | function 실행 전체 | 정적배열 실행 |
| 1단계 (정적배열 끝난 뒤) | — | (계속 function) | 공장제어쉘 파일 모드 | (계속 function) | 공장제어쉘 파일 모드 보조 |
| 2단계 초반 | class 정적 오류 | class 파싱(선언/상속/instanceof) | class 파싱(필드/this/super) | class 인스턴스/필드/생성자 | class 메서드/상속 체인/오류 |
| 2단계 후반 | class 오류 마무리 → import 검사 | (class Assembler에서 1명만 유지) | import 파싱+로더 (또는 A와 교대) | class 마무리 | class 마무리 |
| 3단계 | 정적 바인딩 → 상수 폴딩 (순서대로) | 공장제어쉘 디버그 - Stepping | 공장제어쉘 디버그 - Watch | 변수 조회 로직 변경 | Test Double 검증 |

> "2단계 후반"은 실제로는 칼같이 나뉘지 않는다. class의 Assembler
> 작업(선언/상속/instanceof, 필드·this/super 파싱)이 먼저 끝나는 시점에
> 맞춰 그 담당자가 import로 넘어가면 되고, 어느 쪽(A/B)이 먼저 끝날지는
> 실제 진행 상황을 보고 그때 다같이 정하면 된다.

## 의존 관계

```
function ──────┬─────────► class
               │
               └─────────► import (선언만 담고 있는 파일을 가져오므로
                                    function이 먼저 있어야 의미가 있음)

정적배열 ───────────────────────────► (독립적, 언제든 시작 가능)

공장제어쉘(프롬프트/파일 모드) ───────► (독립적, 언제든 시작 가능)

function + class + import + 정적배열
        (스코프를 만드는 구조가 전부 갖춰진 뒤) ─────► 실행전 최적화
                                                        (정적 바인딩은
                                                         함수/클래스
                                                         스코프까지
                                                         전부 고려해야
                                                         정확해짐)

공장제어쉘(디버그 모드) ◄──── 언어 기능이 어느 정도 갖춰진 뒤 붙이는 게
                              디버깅해볼 대상이 있어 검증하기 쉬움
```

**핵심 이유**
- `class`의 메서드 호출·생성자 호출은 `function`의 호출 규약(파라미터
  바인딩, return 처리)을 그대로 재사용하는 구조이므로 `function`이
  먼저 끝나야 한다.
- `import`로 가져오는 파일 안에는 함수 선언이 담기므로, `function`이
  없으면 `import`도 테스트할 수 없다.
- `실행전 최적화`(정적 바인딩)는 지역 변수가 몇 단계 위 스코프에
  있는지 계산하는 작업이라, 스코프를 만드는 모든 문법(블록, 함수,
  클래스 메서드)이 먼저 구현되어 있어야 빠짐없이 정확하게 계산할 수
  있다. 그래서 언어 기능 마지막 단계로 둔다.
- `정적배열`과 `공장제어쉘`의 프롬프트/파일 모드는 다른 기능과 얽히지
  않는 독립적인 작업이라 아무 때나 병행 가능하다.

## 진행 단계

### 1단계 (동시 시작)
- **function** — 함수 선언/호출/return/재귀 + 관련 오류 검사
- **정적배열** — Token/Expr 추가 + 생성/읽기/쓰기 + 런타임 오류
- **공장제어쉘 - 파일 모드** — `.txt` 실행, 파일 없음/런타임 오류 처리
  (기존 프롬프트 모드는 이미 있음)

### 2단계 (function 완료 후 시작)
- **class** — 선언/인스턴스/필드/메서드/this/생성자/상속/super/instanceof
  + 관련 오류 검사 (팀 전원 투입)
- **import** — Library import, alias, 순환/중복 import 오류 (class의
  Assembler 쪽이 어느 정도 마무리된 뒤, 그 인원이 넘어와서 시작)

> class와 import 사이에는 기술적 의존성이 없지만(둘 다 function만
> 있으면 됨), 5명뿐이라 둘을 동시에 풀 인원으로 돌릴 수는 없다. class가
> 손이 더 많이 가고 위험도가 높으므로 먼저 전원 투입하고, class의
> Assembler 작업(선언/상속/instanceof, 필드·this/super 파싱)이
> 안정되면 그중 1명 + Checker 담당이 import로 넘어가고, 나머지는
> class의 Executor 쪽(메서드/상속 체인/오류 처리)을 마저 끝내는 식으로
> 다같이 정한다.

### 3단계 (function, class, import, 정적배열 모두 병합된 후 시작)
- **실행전 최적화** — 정적 바인딩(변수 거리 계산), 상수 연산 최적화,
  Test Double 검증
- **공장제어쉘 - 디버그 모드** — stepping(step/next/break/continue),
  watch/inspect

> Checker가 1명뿐이라 거의 모든 기능에 Checker 몫의 작업이 걸려 있다.
> 전체 진행 속도가 그 담당자에게 좌우되기 쉬우므로, Checker 작업은
> "꼭 필요한 최소 범위"부터 먼저 처리하고 나머지는 뒤로 미루는 식으로
> 우선순위를 다같이 정한다.

## 기능별 상세 역할 분담

### function

1단계에서는 function과 정적배열을 완전히 다른 2개 조로 나눠 동시에
진행한다. function은 Assembler A + Executor C + Checker, 정적배열은
Assembler B + Executor D가 맡는다 (두 트랙이 서로 다른 파일을 건드려서
충돌이 없다).

| 담당 | 작업 |
| --- | --- |
| Assembler A (단독) | `Func`/`return` 토큰 추가, 함수 선언 파싱(`FunctionStmt`), 함수 호출 파싱(`CallExpr`), return 파싱(`ReturnStmt`) |
| Checker | 파라미터 이름 중복 검사, 함수 외부 return 검사 |
| Executor C (단독) | 호출 시 새 스코프 생성·파라미터 바인딩·재귀 호출, return 처리(예외/시그널), 런타임 오류(호출 불가 대상, 인자 개수 불일치) |

### class

| 담당 | 작업 |
| --- | --- |
| Assembler A | `Class` 키워드, `:`(상속) 파싱, `instanceof` 연산자 파싱 |
| Assembler B | 필드 접근(`.`) get/set 파싱, `this`/`super` 파싱 |
| Checker | this/super 외부 사용, 자기 자신 상속, 부모 없는 클래스의 super 사용, init에서 return — 전부 AST 구조만으로 판단 가능한 정적 오류 |
| Executor C | 인스턴스·필드 저장소, 생성자(init) 자동 호출 |
| Executor D | 메서드 호출(this 바인딩), 상속 체인 탐색, super 호출, instanceof 판정, 런타임 오류(비클래스 상속, 없는 필드/메서드 접근) |

class는 6개 기능 중 손이 가장 많이 가는 영역이므로, function이 어느 정도
안정된 뒤 팀 전체가 이어서 붙는 것을 권장한다. 다만 담당 라인은
function 때와 그대로 이어지지 않는다 — 여기서는 Assembler A(Class/상속/
instanceof)가 Executor D(상속 체인/instanceof 판정)와, Assembler
B(필드 접근/this/super 파싱)가 Executor C(필드 저장소)와 서로 맞물린다.
기능마다 "누구와 누가 짝인지"는 이렇게 달라질 수 있으니, 매번 표를
보고 실제로 같은 대상을 다루는 사람끼리 소통하면 된다.

### 정적배열

function 트랙(A·C·Checker)과 동시에, 나머지 두 명이 이 기능을 완전히
맡아 끝낸다.

| 담당 | 작업 |
| --- | --- |
| Assembler B (단독) | `[`/`]` 토큰, 인덱스 읽기/쓰기 파싱 |
| Checker | 할 일 없음 (전부 런타임 오류) |
| Executor D (단독) | `Array(n)` 생성, 인덱스 읽기/쓰기, 범위·타입 런타임 오류 |

Checker 몫이 없는 기능이라 Assembler·Executor 각 1명(B, D)만으로
충분하고, 이 둘은 function 트랙(A, C)과 겹치는 파일이 없어 완전히
독립적으로 병행 가능하다. 정적배열이 먼저 끝나면 B·D는 2단계
class 작업에 조기 합류한다.

### import

class보다 작은 기능이라 Assembler 1명이면 충분하다. class에서
먼저 손을 뗀 사람(A 또는 B, 실제로는 그때 상황에 맞춰 결정)이
넘어와서 아래를 전부 맡는다.

| 담당 | 작업 |
| --- | --- |
| Assembler (class에서 넘어온 1명) | `import ... alias ...` 문법 파싱 → `ImportStmt` 생성, 대상 파일을 읽어 재귀적으로 조립하는 로더, import 문법 오류·파일 없음·순환 import 감지 (지금 불러오는 중인 파일 목록을 들고 있어야 하므로 파싱과 로더를 한 사람이 순서대로 처리) |
| Checker | 같은 scope 중복 import, alias 충돌, 반복문 내부 import 검사 (기존 스코프별 이름 추적 로직 재사용) |
| Executor | 관여 적음 (alias 네임스페이스 접근 정도) — class Executor(C, D)가 계속 class를 마무리하므로 이 기능에서는 굳이 배정하지 않아도 됨 |

function이 끝난 뒤에야 실제 테스트(불러올 함수가 있어야 함)가 가능하고,
Checker 시간도 필요하므로 class의 Checker 몫이 어느 정도 정리된 뒤에
시작하는 편이 좋다.

### 실행전 최적화

| 담당 | 작업 |
| --- | --- |
| Checker | 정적 바인딩(변수 거리 계산), 상수 연산 최적화(수식 합치기) — 둘 다 Checker 몫이라 순서대로 처리 |
| Executor C 또는 D (1명) | Checker가 계산한 거리로 변수를 조회하도록 조회 로직 변경 |
| 나머지 전원 | Test Double로 "스코프를 안 거슬러 올라가는지" / "연산 횟수가 0이 되는지" 검증 |

이 항목은 Checker 담당에게 작업이 몰리는 구간이므로, Assembler A/B와
남는 Executor 1명은 이 기간 동안 공장제어쉘로 먼저 넘어가는 것을
다같이 정해두는 걸 권장한다.

### 공장제어쉘

Assembler/Checker/Executor 어디에도 속하지 않는 새로운 영역(CLI, 셸 실행
루프)이라 기존 소속과 무관하게 그때그때 여유 있는 인원이 맡는다.

| 담당 | 작업 |
| --- | --- |
| 1명 (파일 모드) | CLI 인자 파싱, 파일 읽기, 파일 없음/런타임 오류 처리 — 별도 언어 기능 의존 없이 아무 때나 시작 가능 |
| 1명 (디버그 모드 - Stepping) | Executor 실행 루프에 정지 훅 추가 (`step`/`next`/`break`/`continue`) — Executor 담당자(C 또는 D)와 협업 필요 |
| 1명 (디버그 모드 - Watch) | 변수 저장소 조회 명령 (`watch`/`watches`/`inspect`) — Stepping과 별개로 진행 가능 |

파일 모드는 정적배열처럼 다른 기능의 손이 덜 가는 1단계에 먼저
끝내두고, 디버그 모드는 실행전 최적화로 Checker 쪽이 바쁠 때 Executor/
Assembler 여유 인원이 맡는 흐름을 권장한다.

## 확인 결과 (전체 검토용)

- **인원 쏠림**: 3단계(실행전 최적화)에서 Checker 담당자 혼자 정적
  바인딩 + 상수 폴딩을 순서대로 처리해야 하는 구간이 유일한 병목이다.
  이 시간 동안 나머지 4명은 공장제어쉘/Test Double 검증으로
  분산해뒀으므로 놀리는 인원은 없다.
- **A/B, C/D 역할 중복 없음**: 1단계는 A/C(function)와 B/D(정적배열)가
  아예 다른 기능을 맡아 겹치지 않고, 2단계(class)는 A(Class/상속/
  instanceof)·B(필드/this/super)처럼 서로 다른 문법 영역을 나눠서
  같은 파일의 같은 함수를 둘이 동시에 고칠 일이 없다.
- **의존성 위반 없음**: class·import는 function 완료 후로, 실행전
  최적화는 function/class/import/정적배열 완료 후로 배치되어 있어
  앞서 정리한 의존 관계 순서를 그대로 따른다.
- **정적배열 우선순위**: Checker 작업이 없는 유일한 기능이라 1단계에
  가장 가볍게 배치했다. B·D 조합처럼 function을 맡지 않은 인원으로
  채우면 1단계 전체 인력이 낭비 없이 채워진다.

## 진행 팁

- 기존 유닛 소속(Assembler 2 / Checker 1 / Executor 2)은 그대로 유지하고,
  기능별 표에서 자기 담당 줄만 보고 작업하면 된다.
- Checker가 병목이 되는 구간(실행전 최적화, import)에는 다른 인원이
  공장제어쉘처럼 유닛에 안 묶인 작업으로 이동해 대기 시간을 줄인다.
- 각 단계 끝에는 병합(merge) 체크포인트를 두고, 다음 단계 시작 전
  기존 UnitTest가 전부 통과하는지 확인한다 (유의사항 참고).
