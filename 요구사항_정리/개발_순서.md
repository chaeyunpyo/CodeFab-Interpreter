# 개발 순서 및 역할 분담 (5인 기준)

6개 요구사항(function, class, 정적배열, 실행전 최적화, import, 공장제어쉘)
사이의 의존 관계를 기준으로 진행 순서를 정리한다.

## 의존 관계

```
function ──────┬─────────► class
               │
               └─────────► import (선언만 담고 있는 파일을 가져오므로
                                    function이 먼저 있어야 의미가 있음)

정적배열 ───────────────────────────► (독립적, 언제든 시작 가능)

공장제어쉘(프롬프트/파일 모드) ───────► (독립적, 언제든 시작 가능)

function + class + import + 정적배열
        (스코프를 만드는 구조가 전부 갖춰진 뒤) ─────► 실행전 최적화
                                                        (정적 바인딩은
                                                         함수/클래스
                                                         스코프까지
                                                         전부 고려해야
                                                         정확해짐)

공장제어쉘(디버그 모드) ◄──── 언어 기능이 어느 정도 갖춰진 뒤 붙이는 게
                              디버깅해볼 대상이 있어 검증하기 쉬움
```

**핵심 이유**
- `class`의 메서드 호출·생성자 호출은 `function`의 호출 규약(파라미터
  바인딩, return 처리)을 그대로 재사용하는 구조이므로 `function`이
  먼저 끝나야 한다.
- `import`로 가져오는 파일 안에는 함수 선언이 담기므로, `function`이
  없으면 `import`도 테스트할 수 없다.
- `실행전 최적화`(정적 바인딩)는 지역 변수가 몇 단계 위 스코프에
  있는지 계산하는 작업이라, 스코프를 만드는 모든 문법(블록, 함수,
  클래스 메서드)이 먼저 구현되어 있어야 빠짐없이 정확하게 계산할 수
  있다. 그래서 언어 기능 마지막 단계로 둔다.
- `정적배열`과 `공장제어쉘`의 프롬프트/파일 모드는 다른 기능과 얽히지
  않는 독립적인 작업이라 아무 때나 병행 가능하다.

## 진행 단계

### 1단계 (동시 시작)
- **function** — 함수 선언/호출/return/재귀 + 관련 오류 검사
- **정적배열** — Token/Expr 추가 + 생성/읽기/쓰기 + 런타임 오류
- **공장제어쉘 - 파일 모드** — `.txt` 실행, 파일 없음/런타임 오류 처리
  (기존 프롬프트 모드는 이미 있음)

### 2단계 (function 완료 후 시작)
- **class** — 선언/인스턴스/필드/메서드/this/생성자/상속/super/instanceof
  + 관련 오류 검사
- **import** — Library import, alias, 순환/중복 import 오류

### 3단계 (function, class, import, 정적배열 모두 병합된 후 시작)
- **실행전 최적화** — 정적 바인딩(변수 거리 계산), 상수 연산 최적화,
  Test Double 검증
- **공장제어쉘 - 디버그 모드** — stepping(step/next/break/continue),
  watch/inspect

## 기존 팀 구성 기준 역할 분담

지금까지 Assembler 2명 / Checker 1명 / Executor 2명 구조로 개발해왔으므로,
새 기능도 이 소속을 그대로 유지한 채 기능별로 "각자 자기 유닛에서 할 일"을
나눠 맡는 방향으로 정리한다. Node 정의(Stmt/Expr에 어떤 필드가 필요한지)만
관련자끼리 먼저 합의해두면, 그 다음부터는 Assembler 2명 / Checker 1명 /
Executor 2명이 각자 자기 유닛 안에서 병렬로 작업할 수 있다.

> Checker가 1명뿐이라 거의 모든 기능에 Checker 몫의 작업이 걸려 있다.
> 전체 진행 속도가 Checker 담당자에게 좌우되기 쉬우므로, Checker 작업은
> "꼭 필요한 최소 범위"부터 먼저 처리하고 나머지는 뒤로 미루는 식으로
> 우선순위를 조정하는 것을 권장한다.

### function

| 유닛 | 방향 |
| --- | --- |
| Assembler (2명) | `Func`/`return` 토큰 추가, 함수 선언·호출·return 파싱 (Node 정의는 이 둘이 먼저 합의) |
| Checker (1명) | 파라미터 이름 중복 검사, 함수 외부 return 검사 |
| Executor (2명) | 호출 시 스코프 생성·파라미터 바인딩·재귀 처리 1명, return 처리 및 런타임 오류(호출 불가 대상/인자 개수 불일치) 1명 |

### class

| 유닛 | 방향 |
| --- | --- |
| Assembler (2명) | `Class`/`:`(상속)/`this`/`super`/`instanceof` 파싱 — function에서 만든 호출 파싱을 재사용 |
| Checker (1명) | this/super 외부 사용, 자기 자신 상속, 부모 없는 클래스의 super 사용, init에서 return 검사 (모두 AST 구조만 보고 판단 가능한 정적 오류) |
| Executor (2명) | 인스턴스·필드 저장소·생성자 1명, 메서드 호출(this 바인딩)·상속 체인·super·instanceof·런타임 오류(비클래스 상속, 없는 필드/메서드) 1명 |

class는 6개 기능 중 손이 가장 많이 가는 영역이므로, function이 어느 정도
안정된 뒤 팀 전체가 이어서 붙는 것을 권장한다.

### 정적배열

| 유닛 | 방향 |
| --- | --- |
| Assembler (2명 중 1명이면 충분) | `[`/`]` 토큰, 인덱스 읽기/쓰기 파싱 |
| Checker | 정적으로 검사할 게 거의 없음 (전부 런타임 오류) — 이 기능에서는 보조 인력 없이 진행 |
| Executor (2명 중 1명이면 충분) | `Array(n)` 생성, 인덱스 읽기/쓰기, 범위·타입 런타임 오류 |

Checker 몫이 없는 기능이라, Assembler/Executor 각 1명씩만 투입하고 나머지
인원은 동시에 function/class 쪽에 집중할 수 있다.

### import

| 유닛 | 방향 |
| --- | --- |
| Assembler (2명) | `import ... alias ...` 파싱, 대상 파일을 읽어 재귀적으로 조립, import 문법 오류·파일 없음·순환 import 검사 (재귀적으로 파일을 읽는 과정 자체가 Assembler 몫이라, "지금 불러오는 중인 파일 목록"을 Assembler가 들고 있어야 순환 import를 자연스럽게 감지할 수 있다) |
| Checker (1명) | 같은 scope 중복 import, alias 충돌, 반복문 내부 import 검사 (기존에 있는 스코프별 이름 추적 로직을 그대로 재사용 가능) |
| Executor | 관여 적음 (alias 네임스페이스 접근 정도) |

function이 끝난 뒤 시작해야 실제 테스트(불러올 함수가 있어야 함)가 가능하다.

### 실행전 최적화

| 유닛 | 방향 |
| --- | --- |
| Checker (1명) | 정적 바인딩(변수 거리 계산) + 상수 연산 최적화(수식 합치기) — 둘 다 Checker 담당이라 순서대로 처리 필요 |
| Executor (2명 중 1명) | Checker가 계산한 거리로 변수를 조회하도록 조회 로직 변경 |
| 전체 | Test Double로 "스코프를 안 거슬러 올라가는지" / "연산 횟수가 0이 되는지" 검증 |

이 항목은 Checker 담당자 1명에게 몰리는 구간이므로, 다른 인원은 이 기간
동안 공장제어쉘 쪽으로 먼저 넘어가는 것을 권장한다.

### 공장제어쉘

Assembler/Checker/Executor 어디에도 속하지 않는 새로운 영역(CLI, 셸 실행
루프)이라 기존 소속과 무관하게 그때그때 여유 있는 인원이 맡는다.

| 유닛 | 방향 |
| --- | --- |
| 파일 모드 | CLI 인자 파싱, 파일 읽기, 파일 없음/런타임 오류 처리 — 별도 언어 기능 의존 없이 아무 때나 시작 가능 |
| 디버그 모드 - Stepping | Executor 실행 루프에 정지 훅 추가 (`step`/`next`/`break`/`continue`) — Executor 담당자와 협업 필요 |
| 디버그 모드 - Watch | 변수 저장소 조회 명령 (`watch`/`watches`/`inspect`) — Stepping과 별개로 진행 가능 |

파일 모드는 정적배열처럼 다른 기능의 손이 덜 가는 시점에 먼저 끝내두고,
디버그 모드는 실행전 최적화로 Checker가 바쁠 때 Executor/Assembler 여유
인원이 맡는 방식을 권장한다.

## 진행 팁

- 기존 유닛 소속(Assembler 2 / Checker 1 / Executor 2)은 그대로 유지하고,
  기능별 표에서 자기 유닛 줄만 보고 작업하면 된다.
- Checker 담당자가 병목이 되는 구간(실행전 최적화, import)에는 다른
  인원이 공장제어쉘처럼 유닛에 안 묶인 작업으로 이동해 대기 시간을
  줄인다.
- 각 단계 끝에는 병합(merge) 체크포인트를 두고, 다음 단계 시작 전
  기존 UnitTest가 전부 통과하는지 확인한다 (유의사항 참고).
